# YT Learning Loader

A self-contained local learning webapp: scrape YouTube channels, let an AI
agent turn videos into structured learnings and interactive lessons, and
build a personal skill library from what you've learned. Python standard
library only — no frameworks, no build step, one folder, runs locally.

## What it does

- **Scrapes YouTube** — add single video URLs or whole channels; downloads
  metadata, thumbnails, and transcripts (yt-dlp + the Innertube API).
- **AI-extracted learnings** — per video: summary, skills, key points with
  timestamps, and a mermaid diagram, generated by a durable agent engine (Pi
  Durable sidecar, Kimi For Coding model; falls back to the Kimi Code CLI).
  Skill names are auto-normalized against a canonical taxonomy so the library
  stays distinct as it grows.
- **Teach Me workspaces** — freestyle topics or whole videos. An agent
  interviews you about your goals, confirms a mission, then builds numbered,
  self-contained HTML lessons (with quizzes, exercises, and cheat sheets)
  that open right in the app. Finished workspaces become installable
  `SKILL.md` files.
- **Skill library** — "Known skills" (from learned videos + distilled
  workspace skills) vs "skills to learn", with one-click teach-me jumps;
  skills install into `~/.kimi-code/skills` for use in any agent session.
- **14 tabs** — Overview, Teach Me, Visualization (mermaid diagrams with
  zoom), Relationships (cross-video skill graph), Videos (sortable table +
  scraping jobs), Learned, My Skills, Profile, Tests (in-app test runner),
  Structure (file map with peek-inside previews), Console (standalone agent),
  Network (machines and their sessions), CUA Spaces (VM fleet), Settings.

Three printable infographics document the system:
`architecture-infographic.html` (the whole map),
`infographic-pi-durable.html` (the durability model),
`cua-spaces-infographic.html` (the CUA toolbox) — each served by the app and
printable to PDF via the browser.

## Quickstart (Windows)

```bat
start.bat
```

or manually:

```bat
.venv\Scripts\python.exe launch.py    :: runs the test suite, then serves
```

Then open http://127.0.0.1:8471 (the browser opens automatically).
Requires Python 3.15 in `.venv` (already present).

## LAN clients (VMs & other devices)

By default the app binds `127.0.0.1` — only this machine can use it. To let
other devices or VMs on your network reach it:

1. **Settings tab → "LAN / other devices"**: set **Host** to `0.0.0.0`
   (restart required) and optionally set a **LAN token**.
2. **Windows firewall**: allow inbound TCP on the port (default 8471) —
   Settings → Privacy & security → Windows Security → Firewall → "Allow an
   app", and allow `python.exe`; or from an elevated prompt:

   ```bat
   netsh advfirewall firewall add rule name="YT Learning Loader" dir=in action=allow protocol=TCP localport=8471
   ```

3. **What clients see**: after restart the server prints the URLs to open,
   e.g. `http://192.168.1.50:8471`, and the Settings tab shows them in a
   read-only panel (`GET /api/lan`). If a token is set, clients are prompted
   for it once per browser tab (sent as the `x-ytl-token` header; the
   `?token=` query param works too — handy for sharing links).
   Remote VM hosts (a second laptop running cua VMs) also appear in the
   Network tab: they register themselves via
   `scripts/laptop-vm/Register-Nodes.ps1` — see that folder's README.

**Security note**: the app can run agent shell commands (the Console tab and
teach workspaces drive a coding agent), so exposing it to a network means
exposing that power. On any network you don't fully trust, set a LAN token;
on a trusted home LAN it stays optional. The agentd sidecar itself always
stays on `127.0.0.1` regardless — only server.py gets exposed, and the token
gate covers every `/api/` route. Everything still stays inside your LAN; no
traffic leaves the machine except to the model provider as before.

## The Network tab

One card per **machine**, its agent **sessions** listed inside:

- `local` — this machine's durable conversations (teach consoles, the
  consultant console, analysis batches, distillations, delegated tasks).
- One card per sandbox (containers and QEMU VMs) — a VM with an installed
  agent is online and lists its *own* live sessions.
- `remote @ <host>` nodes — VMs on a second laptop, registered by the beacon
  (see *CUA Spaces* below); presence works without an agent, sessions appear
  when the guest exposes one.

Sessions show a live status (working / idle / last-error), color-coded type
chips, and auto-refresh every few seconds. A **×** on a row hides the session
from the view — the transcript stays stored, nothing is deleted. Stopped or
stale machines collapse under a "stopped VMs" toggle so the view stays clean.

## The Console tab

A standalone agent you can consult about anything — no workspace, no video.
One persistent conversation per machine: the **"Run on"** selector routes it to
the master or to any VM that has an agent installed (`console:main` exists
once per node; the master's conversation is untouched when you switch). The
Console tab is also the fastest way to prove a VM agent is real: ask for
`hostname && pwd` — the answer is the VM's, not the master's.

## CUA Spaces (VMs as clients)

The **CUA Spaces** tab creates throwaway client machines from inside the app,
using [cua](https://github.com/trycua/cua) (open-source "computers for AI
agents"). It drives the `cua` CLI on this machine:

```bat
cua sb create ubuntu --name dev   :: Ubuntu sandbox (gVisor container; WSL2 required on Windows)
cua sb exec dev uname -a
cua sb rm dev
```

- **Install**: `irm https://cua.ai/install.ps1 | iex` in PowerShell (Windows)
  or `curl -fsSL https://cua.ai/install.sh | bash` (macOS/Linux). No sign-in
  is needed for local sandboxes. The installer is interactive, so the tab
  shows the command with a copy button instead of running it for you.
- **What the app adds**: a tab that lists sandboxes (`GET /api/cua/status`)
  and streams create/remove as background jobs
  (`POST /api/cua/sandboxes`, `POST /api/cua/sandboxes/remove` — poll
  `/api/agent/job/<id>` like agent jobs). Sandboxes also appear as VM nodes in
  the Network tab.
- **VMs live outside the repo**: sandboxes, the cua CLI, and its images are
  installed on your machine (~/.cua and friends), nothing is vendored into
  this repository. Delete a VM with the tab's delete button or
  `cua sb rm <name>`; uninstall cua itself per its docs.
- **Revertibility**: reverting the feature is `git revert` of its commits —
  no binaries, services, or repo files are left behind by the feature itself
  (pre-existing sandboxes you created would need `cua sb rm` by hand).

**Connect a second laptop as a device.** The CUA Spaces tab can also prepare a
second Windows laptop entirely from here: press *Connect device* for a pairing
code, run the printed one-liner in PowerShell on the laptop (it pairs and
starts polling), then use the per-device buttons — Install VM stack (locked
once it succeeded), Create VM / Create 3 VMs (blank name → next free
`ytl-vm-N`; the container engine starts Docker Desktop itself when it is off) —
whose output streams into the shared job transcript. A successful VM creation
automatically starts the laptop's beacon, so its machines appear in the
Network tab as `remote @ <host>` nodes within a heartbeat. Remote nodes also
get an **Open desktop** button that opens the VM's Ubuntu desktop in a browser
on the laptop (`cua sb view`). See `scripts/laptop-vm/README.md` for what runs
on the laptop. Each sandbox row on this machine also has a **Desktop** button
(`POST /api/cua/sandboxes/view` — captures the viewer URL from `cua sb view`
and opens it in a browser tab, ~1 h ticket; use Chrome/Edge if a codec error
appears) and a **Terminal** button (raw bash in the browser).

**Agents inside laptop VMs (reverse relay).** The same per-device buttons can
turn a laptop QEMU VM into a full agent node that the master drives like any
local sandbox: *Install agent* downloads the agentd bundle into the guest
(curl + tar over `cua sb exec` — the guest image has no `cp`/`tail`/`base64`),
*Expose agent* points the in-guest sidecar at the master's reverse relay, and
*Restart agent* reboots it cleanly (kills stale processes via a `/proc` scan,
drops stale SQLite WAL files, rewrites the start script with the relay target
from the master's registry, then health-checks). The relay pairs a guest
dial-in port (18472+i — QEMU publishes no host port, but the guest dials out
through slirp NAT) with a master client port (18473+i); the laptop's beacon
rewrites the registered node endpoint to `http://<master>:<clientPort>`, so
the Network tab shows the VM as an agent node with sessions, and Console /
VM-task conversations run over the relay unchanged. Two hard-won guest
details: `Connection: close` responses end the sidecar's local leg, so the
relay-out re-attaches it without touching the dial (`{end: false}` pipes);
and a SIGKILLed sidecar leaves WAL locks that block the next start, so a
restart always cleans them first.

**Delegate a task to a VM (v1).** The CUA Spaces tab can hand a task to a
sandbox so the agent's *commands* execute on the VM while its thinking and
memory stay in this machine's durable agent conversation: the conversation is
keyed `vmtask:<vm>:<session>` and its instructions force every shell command
through `cua sb exec <vm> -- …`, so nothing runs on the host. Submit one with
`POST /api/agent/vm-task {"vm": …, "task": …}` (optionally `"session"` to name
it); the job streams like any other at `/api/agent/job/<id>`. This needs the
agentd sidecar — the CLI fallback can't carry per-conversation instructions —
and best-effort wakes a suspended VM (`cua sb resume`) before delegating.

**Resume semantics.** A task conversation is just a durable conversation, so
resuming means re-submitting the same key with new instructions: the sidecar
re-applies the (idempotent) per-conversation instructions on every submission,
which is how the same session moves to a different VM. Omitting `session`
starts a fresh one each time.

**Terminal (raw shell).** Each sandbox row has a Terminal button that opens a
persistent raw bash inside that one VM (`POST /api/cua/term/open` — spawns
`cua sb exec -i <name> -- bash` on the host; the pane polls
`/api/cua/term/<id>` and sends lines via `/api/cua/term/<id>/send`). One
terminal per sandbox and one pane at a time; closing the pane ends the shell,
and a terminal nobody has touched for 15 minutes is killed automatically.
ANSI escape codes may appear verbatim — it's a raw shell, not a pty.

In the Network tab these conversations appear under their VM's node (labeled
🛠 task, titled by the session part), and each VM node carries a connection
hint by flavor: a qemu VM reaches this host at `http://10.0.2.2:8471` (its
NAT gateway address; the browser asks for the LAN token), while a container
shares the host's network and uses the plain LAN URL from
Settings → LAN / other devices. Each node renders as its own bordered card —
header row (status, name, kind, session count) on a shaded background with
sessions indented inside — so neighboring nodes no longer blend together,
and session-type chips are color-coded (console blue, distill purple, task
amber, teach green, analysis grey).

## Agents inside VMs (v2)

Beyond exec-delegation, a VM can run the **agent itself**: the same agentd
sidecar that runs on this machine, installed *inside the guest*. Each VM then
is a true agent node with its own long-lived conversations that live on the
VM, show up in the Network tab, and survive the master machine rebooting
(suspend/resume the VM and everything is still there). VMs created by this
app publish the sidecar port from birth (`--service agent=8472` on
`cua sb create`); older VMs get a managed `cua sb port-forward` on a loopback
port from the 18500+ range instead (`vm_nodes.py`).

- **Install agent**: the CUA Spaces tab's per-VM button runs
  `POST /api/cua/provision {"name": …}` — a streaming job that packs
  `agentd/`, copies it into the guest, ships the API key as its own
  chmod-600 `.env` (never printed), runs `npm ci`, starts the sidecar
  detached on `0.0.0.0:8472`, and verifies `/health` from the host. Each step
  has a 10-minute ceiling; re-running it is idempotent. **After a full VM
  restart the processes are gone (files survive) — press Install agent again
  to re-launch.**
- **Console "Run on"**: the Console tab's select routes the conversation to a
  VM's agent. The key stays `console:main`, but each node has its *own*
  `console:main` — the master's conversation is untouched. A node without a
  healthy agent answers 503 with a hint.
- **Native VM tasks**: `POST /api/agent/vm-task` with `"node"` set runs the
  task directly on that VM's sidecar (no `cua sb exec` instructions, cwd
  `/home/cua`); without it you get the v1 exec-delegation from above.
- **`GET /api/vm-nodes`** reports per-VM `{name, online, agent, endpoint}` —
  the CUA tab shows agent ✓/✗ per row from it.

**Security note**: the guest holds your API key, and the sidecar answers
unauthenticated inside its own loopback world — the host only reaches it via
the published endpoint or the managed port-forward on 127.0.0.1. The LAN
token gate on `/api/*` is unchanged and is what keeps LAN clients (VM
browsers included) out of the master's API; the VM agents themselves run with
your key on your LAN, so treat the sandboxes like any machine that can spend
your model quota.

## The AI agent (Pi Durable sidecar + CLI fallback)

Agent features (teach workspaces, learnings generation, skill distillation)
prefer the **agentd sidecar** in `agentd/` — a Node host for the Pi Durable
agent harness with long-lived model conversations. The app starts it
automatically (`npx tsx src/server.ts`, port `agentd_port` in settings,
default 8472; boot log in `data/agent/agentd.boot.log`). Put a
`KIMI_API_KEY` in `agentd/.env`; `agentd/quickstart.ts` is a standalone
end-to-end demo of the harness. When the sidecar or its key is unavailable,
everything falls back to the [Kimi Code CLI](https://www.kimi.com/code) on
PATH — the Tests tab and the teach-tab console badge show which backend is
active.

## Data & privacy

Everything is local by design. `data/videos.json` and `data/learnings/` are
tracked in git as a backup of the curated library; thumbnails, transcripts,
server logs, paired-device records (`data/devices.json` — it holds per-device
tokens), remote-node registrations, and `teach/` workspaces (they contain
your learner profile) are gitignored and never leave the machine.
